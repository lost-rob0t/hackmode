** Authority direction is already decided

- ADR #149 (accepted 2026-08-31): hackmoded is the long-lived host;
  Hackmode owns operation semantics, the capability/provider
  registry, typed validation and canonical mutation APIs, and the
  LISH/Emacs/local control protocol. EPIC #150 invariant: "No second
  scheduler, second operation DB, second graph store or second KB
  authority." #151: clients use a narrow typed local protocol; "the
  transport itself [is not] canonical business state"; "same-image
  callers may use the same Common Lisp protocol directly". hackmoded
  is not implemented yet (#151/#152/#153 open).
- PR #175 (open): =hm= CLI commands are "intentionally thin adapters
  over the same Common Lisp command functions"; a process may own the
  runtime lifetime until hackmoded exists.
- pentest-tool-definitions.org (accepted): provider backends are
  owned by their provider systems; the bridge never re-wraps an
  owned backend; evidence is lossless.

** MCP specification facts (pinned sources)

- Pinned pages (recorded Brave search, 2026-11-23):
  https://modelcontextprotocol.io/specification/draft/server/tools,
  https://modelcontextprotocol.io/specification/draft/schema,
  https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/server/tools.mdx
  (fetched in full), and the versioned 2026-07-28 tools page path.
- Tool = name, title?, description, inputSchema (JSON Schema, 2020-12
  default), outputSchema?, annotations?. =tools/list= supports
  pagination via cursor. =tools/call= result = content blocks +
  structuredContent (object) + isError; a tool returning structured
  content SHOULD also return the serialized JSON in a text block.
- Error taxonomy (2025-06-18, "Error Handling"): protocol errors are
  JSON-RPC errors (unknown tool → -32602); tool execution errors are
  results with =isError: true=.
- Server capability declaration: ={"tools": {"listChanged": ...}}=.
  Security: servers MUST validate all tool inputs, implement access
  controls, rate-limit tool invocations, and "sanitize tool outputs"
  (see Adversarial review for the conflict with Hackmode's lossless
  invariant and its resolution).
- Protocol version is a date string negotiated at =initialize=;
  2024-11-05 and 2025-06-18 and 2026-07-28 all exist; the draft adds
  a =resultType= field. The lab ZAP MCP server and starintel-mcp both
  ship the 2024-11-05 shape; the lab clients send
  =protocolVersion: "2024-11-05"=.

** Tension points found

1. An in-process MCP server owns a runtime lifetime, which ADR #149
   wants to retire in favor of hackmoded. PR #175 establishes the
   sanctioned interim pattern (a process owning the runtime, thin
   adapters over canonical functions), and #151 explicitly allows
   same-image callers of the CL protocol. Resolution in Design.
2. MCP security guidance says servers "sanitize tool outputs";
   Hackmode's regression ledger bans evidence mutation. Resolution in
   Adversarial review.
3. =use-operation= mutates process-global state (chdir, =*db*=,
   =*current-operation*=). Resolution in Adversarial review.

* Design

** Layering (state stays canonical)

#+begin_example
MCP client (OpenCode / Zara / pi / claude …)
        |  stdio, newline-delimited JSON-RPC 2.0
        v
hackmode-mcp transport   (framing, initialize, error taxonomy)
        v
hackmode-mcp catalog     (tool definitions DERIVED from the pentest
        |                 graph + fixed operation/asset tools)
        v
hackmode-mcp dispatch    (argument coercion, canonical calls only)
        v
hackmode canonical APIs  (operations, providers, assets, outbox)
        |
        v
Tek9 operation store     (canonical local state, unchanged)
#+end_example

The server owns no durable state and adds no schema authority, no
provider registry, and no second operation model. The later hackmoded
binding (#151) replaces the bottom arrow with the daemon control
protocol; catalog, schemas, and transport do not change.

** Tool catalog (slice 1)

Operator directive (2026-11-24, recorded correction): *one
Star-Lang-declared tool defines exactly one MCP tool, named verbatim.*
No enum-dispatch meta-tools (the first implementation's
run_recon_tool/run_vuln_scan shape was wrong and is removed). Composed
convenience tools are allowed only as future ADDITIONS on top — every
declared tool must remain individually callable, and no composite ever
replaces or hides a per-tool surface.

Fixed names, snake_case for ecosystem consistency with the operator's
existing servers (zap_*, op_*):

| MCP tool         | source                       | annotations         | summary                                                                 |
|------------------+------------------------------+---------------------+-------------------------------------------------------------------------|
| op_list          | registry                     | readOnly            | list persisted operations + current selection                            |
| op_create        | new-operation                | destructive: no     | create an operation workspace (default root =$HACKMODE_OPERATIONS_DIR=, default =~/hackmode/=) |
| op_use           | use-operation                | destructive: no     | select operation; opens its Tek9 store                                   |
| op_status        | operation-status             | readOnly            | current operation detail                                                 |
| asset_query      | query-assets                 | readOnly            | operation-local assets, optional =type= filter and explicit =limit=      |
| capability_list  | registry + declared catalog  | readOnly            | registered backends ∪ Star-Lang-declared tools with backend status       |
| subfinder, crtsh, massdns, nmap, httpx, katana | declared recon-tool entries | open-world: executes external tools and persists findings | one MCP tool per declared recon tool, dispatched through the canonical provider path |
| nuclei, zap      | declared vuln-tool entries   | open-world: executes external tools and persists findings | one MCP tool per declared vuln tool, dispatched through the canonical provider path |

Per-tool input schemas are DERIVED: the declared message schema
(run-recon-tool / run-vuln-scan) minus the =tool= selector, because the
MCP tool IS the declared tool — properties = runId, target, options
(camelCase names from the message declaration); =target= required,
runId optional at the MCP boundary (server generates a
pattern-conforming id and validates any caller-supplied id against the
declared scalar pattern; the wire message always carries one). Pending
declared tools (nmap/httpx/katana/zap) still appear as callable MCP
tools and answer clean isError results naming the pending backend. Run
tools require an open operation store and fail closed otherwise;
descriptions say to call op_use first and warn that execution is
synchronous in slice 1.

** Schema derivation rules (IR → JSON Schema 2020-12)

| IR shape                                   | JSON Schema                                    |
|--------------------------------------------+------------------------------------------------|
| enum declaration                           | {"type":"string","enum":[<values>]}            |
| scalar :base "string" with :pattern        | {"type":"string","pattern":<pattern>}          |
| scalar :base "string" without :pattern     | {"type":"string"}                              |
| "string" / "integer" / "map"               | {"type":"string"} / {"type":"integer"} / {"type":"object"} |
| (:list T)                                  | {"type":"array","items":<resolve T>}           |

Qualified references resolve recursively against the same graph;
memoized, cycle-safe. The declared pattern is applied server-side to
server-generated ids (the pinned loader does not enforce patterns;
pentest-tool-definitions.org already records that callers must not
rely on it).

** Dispatch table (tool → capability/provider)

| tool     | capability, provider          | status    |
|----------+-------------------------------+-----------|
| subfinder | :subdomain-enumerate, subfinder | registered |
| crtsh    | :subdomain-enumerate, crtsh   | registered |
| massdns  | :dns-resolve, massdns         | registered |
| nuclei   | :vuln-scan, nuclei            | registered |
| nmap     | — (tracker #215)              | pending   |
| httpx    | —                             | pending   |
| katana   | —                             | pending   |
| zap      | — (candidate backend: star-bbp-lab ZAP MCP, slice 2 reconciliation) | pending |

Pending tools appear in capability_list with status pending so agents
see the roadmap, and a run request returns a clean isError result —
never a crash or a silent no-op. Table frozen by test against the
declared enums (every declared tool must appear exactly once).

Input construction: the resolved definition's =input-type= decides the
typed asset built from the string target: hackmode:domain →
=(make-instance 'domain :record <target> :record-type "")=,
hackmode:url → =parse-url=. Unknown input types fail closed. Providers
keep owning their own type checks.

** Result model (lossless)

- structuredContent = {"toolRun": <encoded tool-run document>,
  "job": {id, capability, provider, state, createdCount, assets:
  [projected], error?}}; the same JSON is echoed in a text content
  block (spec back-compat rule).
- The tool-run document is emitted for every run, success or failure:
  status completed/failed (the only states slice 1 can truthfully
  produce), raw map carrying capability, provider, jobId, state,
  createdCount, operation, and the error text when failed. exitCode /
  stdout / stderr are NOT fabricated: provider plumbing for live
  argv/stdout/stderr in tool-run documents is pentest
  slice 2 (already designed there). Until then the evidence trail is
  the provider's own lossless records (exact JSONL finding lines;
  complete stdout+stderr embedded in the job error record), which the
  job error surfaces verbatim in the result. Nothing is truncated.
- asset projection fields: id, kind, value (canonical), operation,
  tool, tags, dateAdded, dateUpdated + kind-specific fields (domain:
  name/type/ips; url: scheme/host/port/path/query; host:
  hostname/ip; finding: type/data/documentId; certificate:
  commonName/notBefore/notAfter; port: port/services).
- asset_query applies no default filtering. An explicit caller-supplied
  =limit= slices the response and sets =truncated: true= with the full
  match count; canonical evidence is untouched.

** Transport

- Newline-delimited JSON-RPC 2.0 over stdio (one message per line,
  UTF-8); logs strictly to stderr; stdout carries protocol traffic
  only.
- initialize: echo the client's protocolVersion when it is in the
  supported set {2024-11-05, 2025-06-18}; otherwise reply with
  2025-06-18 (the server's latest supported version) per version
  negotiation. capabilities: {"tools": {"listChanged": false}} (the
  catalog is static per process). serverInfo: hackmode-mcp 0.1.0.
- notifications/initialized and other notifications: no response.
  ping: {} . Unknown method: -32601. Unknown tool: -32602 (spec
  example, lab precedent). Malformed JSON line: -32700 with id null.
  Lisp conditions inside a handler: result with isError true and the
  condition text — complete, untruncated.
- EOF on stdin exits 0.

** Authority and security

- The server exposes ONLY canonical APIs. It adds no mutation API,
  no direct Tek9 access, no expert write path (the expert layer stays
  passive), and never talks to StarIntel ingest on its own.
- Operation scoping is by construction: run tools and asset_query use
  the open operation store (*db*); with none open they fail closed.
  This is an access boundary on evidence — enforcement by scope, not
  by mutation (regression-ledger rule).
- MCP "rate limit tool invocations" is satisfied in slice 1 by the
  sequential stdio loop (one call at a time, no internal retries of
  effectful calls) plus the providers' own caps; documented per
  zara-mcp invariants (failed effectful calls are not replayed).
- Input validation: schemas are enforced by coercion at dispatch
  (unknown/missing required arguments → isError; enum values checked
  against the graph); the Star-Lang document constructor is the
  second validation layer.

** Packaging

- ASDF system =source/hackmode-mcp/hackmode-mcp.asd= (package
  hackmode-mcp; depends on hackmode, hackmode-starlang, jsown) +
  =hackmode-mcp-tests.asd= (plain assert-based tests like the
  sibling systems).
- Entrypoint =hackmode-mcp:main=: run =*startup-hook*= (opens the
  operations registry), then the stdio loop. It does NOT load
  =~/.config/hackmode/init.lisp= (a headless server image must not
  depend on LISH-oriented user init); recorded as a deliberate
  default. Operations root default =~/hackmode/= (the Emacs
  =hackmode-dir= convention, "where the other operations live"),
  overridable with =HACKMODE_OPERATIONS_DIR=.
- Makefile target =hm-mcp= mirrors the existing =build= target
  (save-lisp-and-die executable). flake.nix is intentionally not
  touched: PR #175 owns flake entrypoints and is unmerged.

* Adversarial review (counterexamples → resolutions)

1. *use-operation chdirs and swaps global state.* Two interleaved
   calls from one client could race — impossible in slice 1 (the
   stdio loop is sequential), but the daemon binding (#151) is the
   real fix; documented as a slice-3 migration note, not hidden.
2. *MCP says sanitize outputs; the ledger bans evidence mutation.*
   Resolution: exact captured values are the product of this server;
   "sanitize" is satisfied by not embedding untrusted output into
   protocol metadata (it travels as result content) and by operation
   scoping as the access boundary. No redaction is introduced, and
   the design says so explicitly so it cannot sneak back in.
3. *Client requests a newer protocol (2026-07-28, draft resultType).*
   Server answers 2025-06-18; spec-compliant clients either accept or
   disconnect cleanly. Upgrade path recorded (add the version +
   resultType emission), no partial pretending.
4. *Giant nuclei stdout floods the client context.* The result carries
   the complete evidence by invariant; bounded consumption is a client
   concern (asset_query with explicit limit; slice-2 pagination).
   Silent truncation would violate the ledger and is not offered.
5. *A scan runs for 30 minutes and the client times out.* Slice-1
   synchronous execution is a documented limitation with warnings in
   tool descriptions; slice 2 moves dispatch onto
   dispatch-capability futures with job polling (the actor path
   already exists and is the canonical boundary).
6. *Agent calls httpx (declared, no backend).*
   Clean isError result naming the pending status and tracker slice;
   capability_list already told it. No partial execution, no fake
   results.
7. *Two processes (Emacs hm image and this server) open the same
   operation store.* Same exposure as running two hm CLI instances
   today (Tek9/LMDB multi-process semantics are unchanged by this
   design); the daemon binding collapses this later. Nothing in this
   design deepens the duplicate-state model (no third registry).
8. *runId collisions across runs.* Server default =
   "hm-<unix>-<counter>" (pattern-conforming, validated); caller
   ids honored so operator intent (reproducible run ids) is preserved.
9. *Catalog drifts from the spec.* It cannot: derived at load from the
   graph, IR version asserted by the bridge, freeze tests pin the tool
   names, schema shapes, and the dispatch table against the declared
   enums.
10. *Derived schema surprises (pattern anchors, map raw).*
    Server-side validation is belt-and-braces (dispatch checks
    required args/enums; the document constructor re-validates wire
    fields); patterns are used for ids only, never assumed enforced
    for callers.
