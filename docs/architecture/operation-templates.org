|-----------------+-------------------------------------------|
| templates/bbp/  | bug-bounty *program* operation (the bounty replacement) |

** templates/bbp/ contents

- =operation.org= :: identity (title, program, platform, policy URL),
  *Scope* =#+NAME: scope= table (target | kind | in-scope | notes)
  with an elisp babel block exporting in-scope rows to
  =.config/targets.txt= (same contract the Emacs client and the
  methodology note use), *Out of scope* section feeding
  =.config/blacklist.txt=, rules/policy notes (eligible-submission
  language left to the program), bounty/reward table, phases
  (recon → freebies → vuln-class passes → report), links to
  methodology.org / assets.org / findings.
- =methodology.org= :: the operator's method as a working checklist:
  Recon & freebies (annotated: subfinder + crt.sh are Hackmode
  =:subdomain-enumerate= backends today; ffuf/nuclei/zap mapping
  noted where a backend exists or is pending), Security
  Misconfiguration (OWASP A05 checklist), XSS (input vectors, common
  params, payload pointers to roam), SQLI, GraphQL, SSTI, CSRF, SSRF
  (bypass lists, instance metadata). Each item is a TODO checkbox;
  each section head lists its Hackmode coverage so an AI (or human)
  knows what is tool-backed vs manual. Payload bodies stay in the
  linked roam nodes; the template links, it does not duplicate.
- =assets.org= :: asset inventory tables (Web/IP/Domain/Services),
  same headings as the live ops.
- =.config/targets.txt=, =.config/blacklist.txt= :: empty seeds
  (the Emacs client creates targets.txt anyway; shipping them makes
  the template standalone).
- =reports/= :: empty dir for program submissions/disclosure
  paperwork (findings/ stays client-managed).

** Deliberately NOT in templates

- No machine-specific automation (the methodology note's
  automation.lost.system endpoints and proxychains fetch) — those are
  the operator's live-environment concerns; the methodology.org links
  the roam note instead of baking endpoints into the tracked tree.
- No runtime scaffolding code in this cycle: =new-operation= stays
  registry-only; template-driven scaffolding (MCP op_create with a
  template argument, LISH parity) is slice 2 and needs its own review
  because it adds a runtime concept (template discovery path).

* Adversarial review

1. *Template drift vs clients.* Extra template files are harmless to
   Emacs (it copies directories) and to the runtime (it only creates
   .hackmode/). The contracts the clients DO enforce
   (.config/targets.txt creation, findings/ creation, .envrc writing)
   are preserved, not duplicated: the template seeds, the client
   overwrites/creates idempotently.
2. *Scope-table export writes into .config/*: the babel block must
   create the directory if missing (f-mkdir via
   `make-directory` in elisp) so a fresh copy works before the Emacs
   client has run. Handled in the block itself.
3. *Leaking the operator's private automation into a public tree:*
   the node-red endpoints stay out (see Deliberately NOT); the
   templates ship placeholder-free, program-agnostic skeletons.
4. *bbp methodology is operator-personal:* it is the operator's own
   directive to encode their method in the product tree; content is
   checklist + links, no third-party text dumps (jhaddix seed is
   attributed in the roam note, and the template links rather than
   copies).
5. *Deleting templates/bounty breaks someone:* nothing in-tree
   consumes template names (selection is interactive directory
   listing); the live ~/hackmode/bounty operation is already copied
   material and is untouched by this change.
6. *Lossless invariants:* templates carry no evidence path; nothing
   here mutates or filters captured data.
